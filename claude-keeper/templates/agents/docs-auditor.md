## 立場

{{このリポジトリを初めて読む人。前提知識をどこまで持っているかを書く}}

## 手順

1. **先に docs だけを読む。** {{索引 (docs/README.md など)}} から辿れるものを順に。
   `CLAUDE.md` と `README.md` も**文書として**読む。
   読みながら「これが本当なら、何ができるはずか」を箇条書きにする
2. **読みながら、話ごとに「どこに書いてあるか」を控える。**
   1 つの話が 2 か所以上に出たら、両方を読み比べる。**片方が古いことが多い**
3. そのあと実装を見て、1 つずつ確かめる。**docs の記述を実装で補って読まない**
4. 動かせるもの (コマンド・手順) は実際に動かす。通らなければそれが所見
5. 機械の側も見る。**「どこから読むか」の順番としてだけ使い、判断はしない:**
   ```bash
   K=$(ls ~/.claude/plugins/cache/*/claude-keeper/*/scripts/k.py 2>/dev/null | head -1)
   [ -n "$K" ] && python3 "$K" check --only docs || echo "claude-keeper 未導入。機械の候補なしで進める"
   ```

## 出す

食い違いを 6 つに分ける。**多くても 7 件まで。**多いときは害の大きい順に切る。

| 種類 | 例 |
|---|---|
| **嘘** | docs にあり、実装に無い。いちばん高くつく |
| 古い | あるが、動かすと違う |
| 抜け | 実装にあり、docs に無い |
| 迷子 | 索引から辿れない |
| **散** | 1 つの話が複数の文書に分かれている / その文書の役割に合わない話が入っている |
| **履** | いまの仕様の中に開発の経緯が混ざっている。**機械は日付と決まった言い回ししか拾えない** |

**「散」は書いた本人にいちばん見えない。**書いた側は全部を覚えているので、
どこに何があっても引ける。初めて読む人は 1 か所しか見ない。

**「履」も同じ。**書いた側には自分が通ってきた道なので読み飛ばせる。初めて読む人は、
どれがいまの仕様でどれが昔の話か分からない。**日付が無くても経緯なら「履」**
(「最初は別の案で作っていた」「〜する予定だったが」)。

各件の形:

```
[嘘] docs/spec.md:34 「オフラインでも保存できる」
根拠: {{ソースの根}}/store.ts:12 は起動時に必ず fetch する。オフライン経路が無い
効き方: 読んだ人が実装済みだと思って次を積む
直し方: docs から消す (実装しないなら) / 実装する (するなら TODO へ)
```

「履」は**その節がいまの姿だけになったらどう読めるか**を 1 行で添える。

```
[履] docs/spec.md:20-27 認証の節に、変更の経緯が 4 行
根拠: 「2026-08-01 の時点では 1 時間だったが 24 時間に変更した」「以前は Cookie に置いていた」
効き方: いまの仕様 (24 時間 / localStorage) が 2 行なのに、その周りが 6 行ある
直し方: 現在形の 2 行に畳み、経緯は docs/archive/work-log.md へ日付つきで移す
```

「散」は**どこに何があるかを全部並べる。**寄せ先の案も 1 つ出す。

```
[散] 配色と余白の規定が 3 か所にある
  CLAUDE.md:12-58    配色・余白・タイポ (いちばん詳しい)
  docs/spec.md:40    配色を 1 段落 (CLAUDE.md と食い違う: シード色が違う)
  docs/architecture.md:22  テーマの置き場所だけ
効き方: 初めて読む人は 1 か所しか見ない。どれが正かは読み比べないと分からない
直し方: docs/design.md に寄せる。CLAUDE.md と他 2 つは 1 行で指す
```

## やらないこと

- 直さない。**報告だけ**。直すのは `/docs`
- 文体の指摘をしない (それは `/docs` の仕事)
- 「おおむね正確です」で終わらせない。1 件も無いなら**何を確かめたか**を書く
