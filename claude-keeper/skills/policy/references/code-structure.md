# 構成の考え方

規約はリポジトリごとに決めるが、決めかねるならここから始める。

## 崩れるのはいつも同じ順番

Claude に順に実装させると、次の順で崩れる。**どれも「1 つずつ足していく」ことの副作用。**

| 段階 | 起きること | 気づける印 |
|---|---|---|
| 1 | 1 つのファイルに足し続ける | 300 行を超える。関数が 50 行を超える |
| 2 | 似た処理が別のファイルに書かれる | 8 行以上そっくりな塊が 2 箇所に出る |
| 3 | 近道の import が入る | domain から infra を呼ぶ |
| 4 | 置き場所に迷ったものが根に落ちる | どの層にも属さないファイルが増える |
| 5 | 古いほうが消されずに残る | どこからも import されないファイルが出る |

**1 と 2 を止めれば 3 以降はほとんど起きない。** 逆に、3 まで進むと直すのは
移動ではなく設計のやり直しになる。だから停止時の指摘は 1 と 2 を先に出す。

## 分けるかどうかの判断

**行数は理由ではなく、合図。** 300 行だから分けるのではなく、300 行になったとき
「2 つの役割が入っていないか」を見る。入っていなければ分けない。

分けてよい合図:

- ファイルの中で、**上半分と下半分で使っている import が違う**
- 関数が「〜して、〜する」と説明される(`and` が入ったら 2 つ)
- テストを書くときに、片方だけを差し替えたくなる

分けてはいけないとき:

- 一緒にしか変わらないものを、行数だけを理由に離す
- 1 ファイルにまとめたほうが読める短い関数を、1 関数 1 ファイルにする

## 共通化するかどうかの判断

**似ているだけでは共通化しない。** 同じ理由で変わるものだけをまとめる。

| 共通化する | 共通化しない |
|---|---|
| 同じ仕様を写した (同じ変更が両方に要る) | たまたま形が同じ (別々の理由で変わる) |
| 3 回目に出てきた | 2 回目。まだ形が定まっていない |
| 業務の規則そのもの | 実験の条件違い・移行中の新旧 |

共通化の行き先は**下**(shared / core)。横に置くと、機能どうしが繋がって
機能で切った意味が消える。**上へ吸い上げるか、下へ落とすか。横に渡さない。**

## 最小構成

```
src/
  domain/          業務の規則。何にも依存しない
  application/     手順。domain を組み合わせる
  infra/           外の世界。DB・HTTP・SDK
  api/             入口。受けて application に渡すだけ
  shared/          道具。業務の言葉を持たない
```

機能で切るなら:

```
src/
  features/<機能>/   画面・状態・その機能の API。機能どうしは呼び合わない
  entities/          業務の型と規則
  shared/            部品。機能の名前を持ち込まない
  pages/             入口。features を並べるだけ
```

**最初から全部作らない。** 2 つ目の機能が来てから `shared/` を作る。
1 つしか無いうちに共通化すると、たいてい間違った形で固まる。

## 入口だけは薄く保つ

api / pages / cli は**受けて渡すだけ**にする。ここに条件分岐が増えると、
テストが書けなくなり、同じ判断が別の入口にも写される。
`limits.file_lines` で入口だけ低い上限を入れておくと、早い段階で気づける。
