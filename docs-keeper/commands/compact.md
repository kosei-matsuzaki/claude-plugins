伸びすぎた docs を読める長さに戻す。
**skill `docs-style` を最初に読む。禁止事項リストがそのまま作業指示になる。**

## 1. 対象を決める

```bash
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/dk.py" check
```

`$ARGUMENTS` にファイル名があればそれだけ。無ければ**上限を超えたファイル**が対象。
上限超過がゼロなら、最も長い 1 ファイルを対象にするか聞いて終わる。

## 2. 削る前に仕分ける

対象を読み、各段落を 3 つに分ける。**削るより先に、行き先を決める。**

| 種類 | 行き先 |
|---|---|
| いまの仕様・設計・手順 | **残す**(文体だけ直す) |
| 実装履歴・試したこと・没案・日付つきの経緯 | **`archive/` へ移す**(消さない) |
| 空虚な前置き・重複した要約・一般論・コードの言い換え | **消す** |

`archive/` へ移すときは、移した先に**日付と、元がどのファイルだったか**を書く。
移した結果、元のファイルに「なぜそうなっているか」が失われるなら、
**1 行に圧縮して残す**(「計画は永続化しない。毎回算出するため」のように)。

## 3. 削る

skill `docs-style` の「直すときの手順」に従う。順序が大事:

1. 構造の禁止(2 節)と内容の禁止(3 節)に当たる**塊を先に消す**
2. 残った本文に言い回しの禁止(1 節)を当てる
3. 見出しの下が空になったら見出しも消す
4. 4 節「残すもの」に当たるものは、**迷ったら残す**

**箇条書きが 5 個以上並んで各項目に説明が付いていたら表にする。**
これだけで 3 割減ることが多い。

## 3b. 記録 (`archive/`) が「割りどき」と言われたら

archive にあるものを archive へ送ることはできない。やるのは**割ること**。

1. 規約の `archive.rotate.by` を見る(`year` なら期間、`version` なら版)
2. `git mv` で分ける。例: `archive/dev-notes-archive.md` →
   `archive/2026-H1.md` と `archive/2026-H2.md`。**日付の境目で切る**
3. **`archive.index` に 1 行ずつ足す。** どの期間に何があるかが分かる粒度で
   (「iOS 提出まわり(2026-08)」のように)。索引に無い記録は無いのと同じ
4. 規約の `layout` と `limits` を新しいファイル名に合わせる

**中身は一切書き換えない。** 記録を圧縮すると、後から引く意味が無くなる。
割るだけ。長さは問題ではなく、引けないことが問題。

### 実験結果は archive へ送らない

「この条件で回したらこうなった」は、あとで**比べる**ために残すもの。
実装履歴と違って捨てられない。表(`results.md` など)に生きたまま置き、
archive へ送るのは**その系統を追うのをやめたと決めたときだけ**。
そのときは**やめた理由を必ず書く**(理由の無い没案は、また試すことになる)。

## 4. 確かめる

- **消した情報が本当に不要か。** 判断・罠・警告・動くコマンドを消していないか
- **リンク切れを作っていないか。** 消した節に他から飛んでいないか grep する
- **archive へ移した分が索引から辿れるか**

## 5. 報告

- ファイルごとに **「420 行 → 180 行」** の形で
- archive へ移した項目の件数と行き先
- **消したもののうち、判断が微妙だったもの**を 2〜3 件挙げる(戻せるように)

git に残っているので取り返せる。それでも、**4 節に当たるものを消したときだけは
必ず報告する。**
