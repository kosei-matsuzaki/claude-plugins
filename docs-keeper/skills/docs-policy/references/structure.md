# docs の構成の考え方

規約はリポジトリごとに決めるが、決めかねるならこの形から始める。
役割で分けると、**どこに書けばいいか迷わなくなり、迷わなければ散らからない。**

## 3 つの層に分ける

| 層 | 何を書くか | 時制 | 例 |
|---|---|---|---|
| **いまの姿** | 現在の仕様・設計。過去の経緯は書かない | 現在形 | `spec.md` `architecture.md` |
| **これから** | 残っている作業だけ | 未来形 | `TODO.md` |
| **記録** | 済んだこと・試したこと・没案 | 過去形・日付つき | `archive/` |

散らかる原因はほぼ 1 つ、**「いまの姿」に「記録」が混ざること**。
「最初は A を試したが B にした」は設計書に書かず `archive/` に送る。
設計書に残すのは「B である。A ではないのは〜だから」の 1 行だけ。

## 最小構成

```
README.md          外から来た人向け。何のリポジトリか
CLAUDE.md          作業前に読む決まりごと・既知の罠
docs/
  README.md        索引。どれをいつ読むか
  spec.md          いまの仕様。やらないと決めたことも
  architecture.md  どう作ってあるか。判断の理由
  TODO.md          残作業だけ
  changelog.md     利用者から見た変更点
  archive/         記録。いまの仕様として読まない
```

出すもの(ストア掲載文・審査情報・リリース手順)が増えてきたら `release/` を足す。
**最初から全部作らない。** 必要になってから足す。

## 索引 (docs/README.md) の書き方

索引は目次ではなく**案内**。ファイル名を並べるだけなら `ls` で足りる。

- 「はじめて触るなら A → B の順」のように**読む順**を書く
- 表の 3 列目は「いつ読むか」。開くかどうかを判断できるように
- `archive/` の節には **「いまの仕様として読まないこと」** と明記する
- 生成物(HTML 化したもの、自動生成の図)は「触らない」と書く

## CLAUDE.md との分担

| | CLAUDE.md | docs/ |
|---|---|---|
| 読む人 | Claude と、作業を始める自分 | 仕様を知りたい人 |
| 中身 | 決まりごと・罠・よく使うコマンド・いまの状態 | 何を作っているか・どう作ってあるか |
| 長さ | 短く保つ。詳細は docs へリンク | 必要なだけ |

CLAUDE.md が伸びたら、**中身を docs へ移してリンクに置き換える。**
CLAUDE.md に残すのは「これを知らないと壊す」ことだけ。

## 新しい md を作りたくなったとき

まず既存ファイルの節で足りないか疑う。**ファイルを増やすのは最後の手段。**
それでも要るなら、先に規約の `layout` と索引に足してから中身を書く。
順序を逆にすると、索引に載らない md が生まれる。
