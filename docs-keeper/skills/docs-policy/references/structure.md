# docs の構成の考え方

規約はリポジトリごとに決めるが、決めかねるならこの形から始める。
役割で分けると、**どこに書けばいいか迷わなくなり、迷わなければ散らからない。**

## 3 つの層に分ける

| 層 | 何を書くか | 時制 | 例 |
|---|---|---|---|
| **いまの姿** | 現在の仕様・設計。過去の経緯は書かない | 現在形 | `spec.md` `architecture.md` |
| **これから** | 残っている作業だけ | 未来形 | `TODO.md` |
| **記録** | 済んだこと・試したこと・没案 | 過去形・日付つき | `archive/` |

散らかる原因はほぼ 1 つ、**「いまの姿」に「記録」が混ざること**。
「最初は A を試したが B にした」は設計書に書かず `archive/` に送る。
設計書に残すのは「B である。A ではないのは〜だから」の 1 行だけ。

## 最小構成

```
README.md          外から来た人向け。何のリポジトリか
CLAUDE.md          作業前に読む決まりごと・既知の罠
docs/
  README.md        索引。どれをいつ読むか
  spec.md          いまの仕様。やらないと決めたことも
  architecture.md  どう作ってあるか。判断の理由
  TODO.md          残作業だけ
  changelog.md     利用者から見た変更点
  archive/         記録。いまの仕様として読まない
```

出すもの(ストア掲載文・審査情報・リリース手順)が増えてきたら `release/` を足す。
**最初から全部作らない。** 必要になってから足す。

## 索引 (docs/README.md) の書き方

索引は目次ではなく**案内**。ファイル名を並べるだけなら `ls` で足りる。

- 「はじめて触るなら A → B の順」のように**読む順**を書く
- 表の 3 列目は「いつ読むか」。開くかどうかを判断できるように
- `archive/` の節には **「いまの仕様として読まないこと」** と明記する
- 生成物(HTML 化したもの、自動生成の図)は「触らない」と書く

## CLAUDE.md との分担

| | CLAUDE.md | docs/ |
|---|---|---|
| 読む人 | Claude と、作業を始める自分 | 仕様を知りたい人 |
| 中身 | 決まりごと・罠・よく使うコマンド・いまの状態 | 何を作っているか・どう作ってあるか |
| 長さ | 短く保つ。詳細は docs へリンク | 必要なだけ |

CLAUDE.md が伸びたら、**中身を docs へ移してリンクに置き換える。**
CLAUDE.md に残すのは「これを知らないと壊す」ことだけ。

## 研究・実験リポジトリのとき

シミュレーション・機械学習・分析のリポジトリは、3 つの層の**まん中が違う**。

| 層 | アプリ | 研究 |
|---|---|---|
| いまの姿 | 仕様・設計 | 定式化・前提・置いた近似(`method.md`) |
| **いまの結果** | — | **`results.md`。全試行を 1 行ずつの表** |
| これから | 残作業 | 残作業 |
| 記録 | 実装履歴 | 打ち切った系統・没案 |

**「いまの結果」がアプリには無い層**で、ここを取り違えると散らかる。

```
docs/
  method.md       何をどう解くか。前提と近似の理由
  results.md      いまの結果。1 試行 1 行の表。伸びたら畳めていないしるし
  reproduce.md    再現手順。データの版・乱数の種・環境・コマンド
  experiments/    1 試行 1 ファイル。results.md の各行の裏づけ
  archive/        追うのをやめた系統。やめた理由つき
```

### 実験結果を archive へ送らない

実装履歴(「最初は A を試したが B にした」)は、結論さえ残れば捨ててよい。
**実験結果は捨てられない。**「特徴量 X で AUC 0.78」は、次の試行と**比べる**ために
残すもので、archive に流すと比較対象を失う。

- 増えるのは正しい。**畳み方**を決める: 表は 1 試行 1 行、詳細は `experiments/` へ
- `results.md` が上限を超えたら、それは「表に畳めていない」しるし。
  行を消すのではなく、**打ち切った系統をまとめて archive へ移す**
- archive へ送るのは「この方向は追わない」と決めたときだけ。**やめた理由を必ず書く**。
  理由の無い没案は、半年後に同じことを試すことになる

### 仕様でも記録でもない 2 つの層

実際のリポジトリには、3 層に収まらないものが 2 つ出てくる。**置き場所を分けておく。**

**提案・レビュー**(`design-review.md` のような)。「こう直したい」という指示書で、
書いた時点の話。**実装が追いつくと嘘になる**ので、索引に
「**仕様ではない。実装と食い違ったら仕様が正**」と明記する。
反映し終わったら archive へ送る(送るときに「どこまで反映したか」を書く)。

**正本データ**(カリキュラム・特徴量カタログ・辞書のような)。中身が増えるのが正しく、
**長さで叱っても意味がない**。`limits` から外すか、うんと広く取る。
実装側に対になるファイル(`curriculum.js` など)があるなら、
**`watch` でその同期を見張る**のが効く。片方だけ直すと静かにずれるため。

### 再現手順は最初に書く

`reproduce.md` は最後に書こうとすると永遠に書かれない。
**最初に骨だけ作り、条件を変えるたびに直す。** 中身は「そのまま動くコマンド」と、
データの版・乱数の種・ライブラリの版。ここが古いと、過去の結果が全部無意味になる。

## 新しい md を作りたくなったとき

まず既存ファイルの節で足りないか疑う。**ファイルを増やすのは最後の手段。**
それでも要るなら、先に規約の `layout` と索引に足してから中身を書く。
順序を逆にすると、索引に載らない md が生まれる。
