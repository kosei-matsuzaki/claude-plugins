散らばった同じコードをまとめる。**まとめてよいものだけをまとめる。**

## 1. 候補を出す

```bash
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/ck.py" check --only dupes
```

2 種類出る。**下のほうが本命。**

| 区分 | 何が出るか |
|---|---|
| 行がそのまま重なっている | コピペ。見つけやすいが、数は少ない |
| **形が似ている関数** | 骨組みが同じで名前と文言が違うもの。**共通化できるものの多くはこちら** |

FE のボタンのように「同じ構造で色と文言だけ違う」ものは、行の一致では
1 件も出ない。形の一致で「5 箇所に同じ形」として出る。

どちらも**候補**。一致しただけで、意味が同じとは限らない。

**機械が出さない重なりもある。** 片方が `for`、片方が `map` で同じ集計をしている
ようなものは、形も一致しない。それを探すのは `/code-keeper:review`。

## 2. 1 組ずつ仕分ける

両方を実際に読む。**読まずにまとめない。** 判断は 1 問:

> **同じ理由で変わるか。** 片方を直すとき、もう片方も必ず直すか。

| 答え | すること |
|---|---|
| 必ず両方直す | **まとめる** |
| 片方だけ直すことがある | **触らない**(たまたま形が同じだけ) |
| まだ 2 回目 | **触らない**。3 回目に出てきてからで遅くない |
| 実験の条件違い・移行中の新旧 | **触らない**。規約の `duplication.ignore` に足す |
| 形は同じだが、片方だけ将来変わると分かっている | **触らない**。台帳に理由を書く(5 節) |

**間違った共通化は、重複より高くつく。** 別々の理由で変わるものを 1 つにすると、
片方のための分岐が生えて、両方が読めなくなる。**迷ったら触らない。**

## 3. まとめる

行き先は**下**。skill `code-policy` の「共通化の行き先」に従う。

1. 共通化した関数の置き場所を決める。**規約の層で、両方から依存してよい層**
   (`shared` / `core` / `lib`)。**横に置かない** — 機能どうしが繋がる
2. 差分を引数にする。**引数が 3 つを超えたら、まとめ方が間違っている**。
   そのときは戻して「まとめない」と報告する
3. 両方の呼び出しを差し替える
4. 元のコードを消す。**残したまま新しいものを足さない**(3 箇所目が生まれる)

名前を先に決める。**共通の名前が付かないものは、共通の概念ではない。**

## 4. 確かめる

- **テストを回す。** 両方の呼び出し元それぞれについて
- 引数の順番を取り違えていないか(同じ型が並ぶときの定番の事故)
- `check --only dupes,layers` で、重複が減り、層の逸脱が増えていないこと

## 5. 報告と、判断を残すこと

- まとめた組と、その行き先
- **まとめなかった組と、その理由**(「別々の理由で変わるため」まで書く)

まとめないと決めたものは、**台帳に書く**。書かないと次のセッションでまた出る:

```bash
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/ck.py" judge \
  --path <check の出力にあるファイル> --key "<check の出力にある鍵>" \
  --decision "まとめない" --why "<理由>" --at <そのときの箇所数> --by "/code-keeper:unify"
```

箇所が増えれば(`at` から 3 割)また指摘される。**判断は永久の免罪符ではない。**
場所ごと見ないと決めたものだけ、規約の `duplication.ignore` に足す。
