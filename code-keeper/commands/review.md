**このコマンドだけは数えない。読む。**

`check` が出すのは「見るべき場所」で、直すべき場所ではない。3667 行のファイルが
分けるべきなのか、2 つのボタンをまとめてよいのか、そのコメントが「なぜ」なのか
言い換えなのかは、**読まないと決まらない**。ここがそれをやる。

## 1. 対象を決める

```bash
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/ck.py" session     # このセッションで触ったもの
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/ck.py" check       # 機械が見つけた候補
```

`$ARGUMENTS` の解釈:

| 引数 | 対象 |
|---|---|
| なし | セッションで触ったファイル(無ければ未コミットの差分) |
| パス | そのファイル / ディレクトリ |
| `--since <ref>` | その参照からの差分 |
| `--all` | リポジトリ全体。**10 ファイルを超えるなら、どこから見るか聞く** |

**読める量に絞る。** 全部を薄く見るより、5 ファイルを最後まで読むほうが役に立つ。

## 2. 読む

対象を実際に読む。`check` の出力は**どこを先に見るかの順番**として使うだけで、
出ていないものも見る(機械が見つけられないものを探すのがこのコマンドの仕事)。

### 見るもの 1 — 共通化できるところ

`check` の「形が似ている関数」は骨組みが一致した候補。**それ以外も探す。**
機械が絶対に見つけられないのは次の 2 つ:

| 種類 | 例 |
|---|---|
| **名前も形も違うが、同じことをしている** | 片方は `for` で、片方は `map` で、同じ集計をしている |
| **同じ概念が別々の形で表れている** | 日付の整形が 3 箇所で別々に書かれている(桁揃えの仕方まで違う) |

まとめてよいかの判断は 1 問だけ: **同じ理由で変わるか。**
FE のボタンのように「見た目は同じ骨組みだが、片方だけ将来 confirm を挟む」なら
**まとめない**。詳しい判断基準は [unify.md](unify.md) の 2 節。

### 見るもの 2 — 構造がこのプロジェクトに合っているか

**正しいアーキテクチャは 1 つではない。** 規約の `layers` は前に決めた形であって、
いまのプロジェクトに合っているとは限らない。次を見る:

- 実際の import の向きは、規約の層と合っているか。**合っていないほうが正しいこともある**
- 機能で切るべきものを役割で切っていないか(逆も)。画面が増えたのに
  `components/` が 1 つに膨らんでいるなら、機能で切り直すとき
- 層の名前が実態を言い当てているか。`utils/` に業務の規則が入っていないか
- **この規模でその構造が要るか。** 小さいうちの過剰な層分けは、ただの遠回り

規約のほうがずれていると判断したら、**`.code-policy.yml` の `layers` を直す提案を出す**
(コードを動かす提案と、どちらが安いかを比べて言う)。`layers` が空なら、
実物の import を見て**層の案を作る**。skill `code-policy` の「層をどう切るか」に従う。

### 見るもの 3 — 命名

- 同じものを指す別々の名前(`user` / `member` / `account` が同じものを指している)
- 違うものを指す同じ名前(`status` が画面ごとに別の意味)
- 名前と中身の食い違い(`getUser()` が保存もしている)

**名前の不一致は、たいてい概念の不一致。** 直すのは名前ではなく、分け方のことがある。

### 見るもの 4 — 抽象の高さ

1 つの関数の中に、高さの違う操作が混ざっていないか。
「注文を確定する」と「文字列を 2 桁で埋める」が同じ関数に並んでいたら、
**行数が短くても**読みにくい。`check` の行数では絶対に出ない。

### 見るもの 5 — コメントの中身

比率では何も分からない。**1 つずつ読んで**、skill `code-comments` の 1 節
(書くもの)と 2 節(書かないもの)のどちらかに仕分ける。

- コメントが 90% でも、全部「なぜ」なら**それでいい**
- コメントが 3% でも、自明なコードなら**それでいい**
- 逆に、比率が適正でも中身が名前の言い換えなら**全部消す**

## 3. 仕分けて、見せる

見つけたものを 3 つに分ける。**直す前に一覧を見せて、承認を取る。**

| 仕分け | 次にすること |
|---|---|
| **直す** | どのコマンドの手順に従うか添える(`split` / `unify` / `relayout` / `comment` / `prune`) |
| **このままでよい** | **理由とともに台帳に書く**(4 節) |
| **規約がずれている** | `.code-policy.yml` の直し方を提案する |

「このままでよい」と「規約を直す」を必ず含める。**全部を直すべきと言うのは、
読んでいない証拠。**

## 4. 判断を残す

「このままでよい」と決めたものは、**必ず台帳に書く**。書かないと、次のセッションで
同じ指摘が出て、最後はプラグインごと黙らされる。

```bash
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/ck.py" judge \
  --path src/components/DangerButton.tsx \
  --key "similar:DangerButton:2" \
  --decision "まとめない" \
  --why "危険操作の確認は独立して読めるほうがよい。片方だけ confirm を挟む予定がある" \
  --at 2 --by "/code-keeper:review"
```

`--key` は `check` の出力にある鍵(`file_lines` / `similar:_delete:7` /
`dup:src/b.ts` / `undocumented:handleOrder` など)。`--at` はそのときの大きさで、
**ここから 3 割伸びたら台帳を無視してもう一度指摘される**(判断は永久の免罪符ではない)。

**機械が出していないもの**(名前の不一致など)は台帳に書かない。台帳は
「機械の指摘を黙らせる」ためのもので、報告に書けば足りる。

## 5. 直す

承認されたものだけを、**1 つずつ**。各コマンドの手順に従う。
まとめて直さない。テストがあれば、1 つ直すごとに回す。

## 6. 報告

- 直したもの
- **このままでよいと判断したものと、その理由**(ここがこのコマンドの成果物)
- 規約を直す提案があれば、その差分
- **読み切れなかった範囲**(あるなら正直に言う)
