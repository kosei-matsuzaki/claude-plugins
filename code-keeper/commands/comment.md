コメントを読める状態に戻す。
**skill `code-comments` を最初に読む。禁止事項リストがそのまま作業指示になる。**

## 1. 対象を決める

```bash
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/ck.py" check --only comments
```

出るのは 5 種類:

| 指摘 | 意味 |
|---|---|
| コメントアウトされたコード | 消す。git に残っている |
| 長すぎるコメント | docs へ移して 1 行のリンクにする |
| コメントが少なすぎる | なぜが残っていない。足す |
| コメントが多すぎる | コードの言い換えが混じっている。減らす |
| 説明の無い長い関数 | 何のためにあるかを 1 行足す |

`$ARGUMENTS` にファイル名があればそれだけ。**一度に 1 ファイル。**

## 2. 順番を守る

skill `code-comments` の 6 節のとおり:

1. **コメントアウトされたコードを消す**(いちばん先。これで量が減る)
2. 残ったコメントを「コードから読み取れるか」で見る。読み取れるものを消す
3. 消した結果、**なぜが失われるところだけ 1 行に圧縮して残す**
4. 説明の無い長い関数に 1 行足す
5. **嘘になっているコメントを直す**(コードと食い違っているもの)

## 3. 足すときの中身

足すのは**コードに書けなかったことだけ**。書く前に自分に聞く:

> これはコードから読み取れるか。読み取れるなら書かない。

`// ユーザーを取得する` の直後に `getUser()` を書かない。
足すのは「なぜ 2 回問い合わせるのか」「なぜここで例外を握りつぶすのか」。

**分からないものには足さない。** 推測でコメントを書くと、嘘が固定される。
分からなければ、その関数を「説明が要る」として報告に挙げて、利用者に聞く。

## 4. 確かめる

- **コードを 1 文字も変えていないこと**(このコマンドはコメントだけを触る)
- 消したコメントに「なぜ」が含まれていなかったか
- 言語ごとの形が既存に揃っているか(docstring / JSDoc / `///`)

## 5. 報告

- ファイルごとに「コメント 42 行 → 18 行、うち新規 5 行」の形で
- **消したもののうち、判断が微妙だったもの**を 2〜3 件
- **推測で書かなかったもの**(利用者に聞くべきもの)を挙げる
