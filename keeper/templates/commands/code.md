**機械は候補しか出せない。**3667 行のファイルを分けるべきか、2 つのボタンを
まとめてよいか、そのコメントが「なぜ」か言い換えかは、**読まないと決まらない**。
ここがそれをやり、決めたぶんだけ直す。

## 1. 対象を決める

```bash
python3 .claude/plugins/keeper/scripts/k.py check --only code
```

| 引数 | 対象 |
|---|---|
| なし | 未コミットの差分 |
| パス | そのファイル / ディレクトリ |
| `--since <ref>` | その参照からの差分 |
| `--all` | 全体。**10 ファイルを超えるならどこから見るか聞く** |
| `--read-only` | 読んで報告するだけ。直さない |

**読める量に絞る。**全部を薄く見るより、5 ファイルを最後まで読むほうが役に立つ。
機械の出力は**どこから読むかの順番**としてだけ使う。

## 2. 読ませる

`.claude/agents/code-steward.md` へ投げる(会話の経緯は渡さない)。
役が置かれていなければ skill `flat-view` を読んで自分で読む。

**機械が絶対に見つけられないもの**を探す。ここが読む理由:

| 種類 | 例 |
|---|---|
| 名前も形も違うが、同じことをしている | 片方は `for`、片方は `map` で同じ集計 |
| 同じ概念が別々の形で表れている | 日付の整形が 3 箇所で別々 |
| 同じものを指す別々の名前 | `user` / `member` / `account` が同じもの |
| 1 つの関数に混ざった高さの違う操作 | 「注文を確定する」と「2 桁で埋める」が並ぶ |
| **この構造がこのプロジェクトに合っているか** | 小さいうちの過剰な層分けは、ただの遠回り |

{{このプロジェクトで特に見るところ。2〜4 行。「移行の残骸」「使い捨てスクリプトの溜まり場」など}}

## 3. 仕分ける

**直す前に一覧を見せて承認を取る。**3 つに分ける。

| 仕分け | 次にすること |
|---|---|
| **直す** | 4 節の該当する手順へ |
| **このままでよい** | **理由とともに台帳へ**(5 節) |
| **規約がずれている** | `.claude/policy.yml` の `code:` を直す提案を出す |

「このままでよい」と「規約を直す」を必ず含める。
**全部を直すべきと言うのは、読んでいない証拠。**

## 4. 直す

承認されたものだけを、**1 つずつ**。テストがあれば 1 つ直すごとに回す。

### 分ける — 伸びたファイル・関数

**行数は理由ではなく合図。**切れ目を探す:

- import の使われ方が上下で違うか
- 説明に「〜して、〜する」が入るか
- 状態を持つ部分と、持たない部分に割れるか

**切れ目が無いなら分けない。**役割が 1 つで長いだけのファイルは、割ると読みにくくなる。

### まとめる — 散った同じもの

判断は 1 問だけ: **「同じ理由で変わるか」。**

- 見た目が同じでも、片方だけ将来 confirm を挟む予定なら**まとめない**
- 行き先は**下**(shared / core)。横に置かない
- **引数が 3 つを超えたらまとめ方が間違っている。**戻す

似ていることと、まとめてよいことは別。

### 置き場所を直す — 崩れた構造

逸脱には 3 通りある。

| 種類 | 直しかた |
|---|---|
| 近道の import | import を直す |
| 置き場所が違うだけ | ファイルを動かす(**承認を取ってから** `git mv`) |
| **規約が実態に合っていない** | **規約のほうを直す。ここを怖がらない** |

`code.layers` が空なら、実物の import を読んで**層の案を作る**。

### 消す — 残ったもの

**間違えると動くコードを消す唯一の手順。**根拠を 2 つ取ってから:

```bash
git log --oneline -3 -- <パス>
grep -rn "<ファイル名やシンボル>" <ソースの根>
```

- **枠組みが名前で拾うものは消さない**(ルーティング・DI・設定から引くもの)。
  規約の `code.dead.entrypoints` に足す
- 一覧を見せて**承認を取ってから**消す
- 消したものは git に残る。それでも、消した一覧は報告に書く

### コメントを直す

skill `code-comments` がそのまま作業指示。順番が大事:

1. **コメントアウトされたコードを先に消す**(git に残っている)
2. コードを読めば分かる説明を消す
3. 失われた「なぜ」を 1 行に圧縮して足す
4. **分からないものには足さない。**推測を書くと、次の人が信じる

比率では何も分からない。90% でも全部「なぜ」ならそれでよく、3% でも
自明なコードならそれでいい。**1 つずつ読んで決める。**

## 5. 判断を残す

「このままでよい」と決めたものは、**必ず `.claude/judgments.yml` に書く。**
書かないと次のセッションで同じ指摘が出て、最後は黙らされる。

```yaml
judgments:
  - key: "similar:DangerButton:2"          # check の出力にある鍵
    path: src/components/DangerButton.tsx
    decision: "まとめない"
    why: "危険操作の確認は独立して読めるほうがよい。片方だけ confirm を挟む予定"
    at: 2                                   # そのときの大きさ。3 割伸びたら言い直す
    date: 2026-09-04
```

**機械が出していないもの**(名前の不一致など)は台帳に書かない。報告に書けば足りる。

## 6. 報告

- 直したもの
- **このままでよいと判断したものと、その理由**(ここが成果物)
- 規約を直す提案があれば、その差分
- **読み切れなかった範囲**(あるなら正直に)
